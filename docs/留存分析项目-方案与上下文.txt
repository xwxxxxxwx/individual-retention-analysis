[0.5] 协作模式(2026-05-17 用户明确)
------------------------------------------------------------

这是一个"教学型项目",不是"代写型项目"。AI 助手的角色定位:

* 像导师,不像外包:用户从黑盒状态开始,需要 AI 一步步指引把项目做完。

* AI 负责:代码编写、环境部署、机械性执行(转 Parquet、跑 SQL、画图脚本、
  推 GitHub 等)。
* 用户负责:分析思路、阈值/口径决策、对结果的业务解读、每一步输出内容的
  整理与反馈、最终叙事(README / 报告)的撰写。
* 节奏:小步快跑。每完成一个 checkpoint 就停下来跟用户对齐,不要把多个
  阶段一口气做完;用户希望对每一步都有判断权。
* 二选一胜过开放题:遇到需要决策的地方(阈值选择、图表类型、指标定义),
  AI 优先给 2-3 个明确选项让用户选,不要丢"你看着办"。

最终交付:GitHub public 仓库 + 中文 README + Notebook 系列 + 可视化呈现页面
(可视化形式 5 切口完成后再定)。

[1] 战略背景:为什么做这个项目
------------------------------------------------------------

1.1 数据分析岗位的核心评估维度
- SQL/Python 数据处理能力
- 统计严谨性(假设检验、置信区间、p 值的合理使用)
- 业务翻译能力(把数据结论翻成业务建议)
- 经典分析框架熟练度:cohort 留存、漏斗、AB 实验、RFM、归因
- 大厂尤其在意:DAU/MAU/留存、A/B 实验体系、用户分群

1.2 Text-to-SQL 项目对数据分析岗位的相对短板
- 整体故事偏 AI 应用工程,而不是数据分析
- 卖点是"分类器、prompt 工程、eval 框架",这些词出现在数据分析面试里频率低
- 可以打的点是手写 120 条 few-shot SQL + 80 条 eval 用例(SQL 熟练度证据),
  但需要重新组织描述

1.3 这个新项目要补什么
- 留存分析(cohort)
- 漏斗分析(funnel)
- 用户分群与画像
- 行为驱动的预测建模(用机器学习预测留存)
- 真实工程压力(亿级行数据的处理决策)

1.4 跟"未来的 A/B 实验项目"的关系
用户计划之后做一个 A/B 实验项目。留存分析是 A/B 实验的前置基础:
- 留存里看到的"曲线衰减、novelty effect"会直接复用进 A/B 项目
- 留存里产出的"指标定义、人群分层"可以作为 A/B 项目里的细分维度
两个项目可以共用部分预处理代码 / 数据集,但应**放在两个独立的 GitHub 仓库**。

[2] 数据集选择
------------------------------------------------------------

主选:Taobao UserBehavior (阿里天池)
=====================================

链接:https://tianchi.aliyun.com/dataset/649

规模:
  - 行数        : 1.0015 亿条
  - 用户数      : 约 98.8 万
  - 商品数      : 约 416 万
  - 类目数      : 约 9,440
  - 时间跨度    : 9 天(2017-11-25 ~ 2017-12-03,涵盖双 12 前后)
  - 文件大小    : CSV ~3.5 GB,转 Parquet 后约 0.62 GB(zstd 压缩)
  - 字段        : user_id / item_id / category_id / behavior_type / timestamp
  - 行为类型    : pv(浏览)/ cart(加购)/ fav(收藏)/ buy(购买)

为什么选它:
1. 字节、美团、京东、阿里的数据分析面试官一眼能认出来,讨论上下文对齐
2. 行为类型齐全 → 漏斗、跨类目偏好、复购预测都能做
3. 真的会逼出工程决策(pd.read_csv 直接 OOM,内存占用 ~8-10 GB)
   → 必须用 DuckDB / Polars / 分 chunk 读 / 转 Parquet
   → 这部分踩坑过程本身就是简历素材

关键坑(必须避开):
- 这是经典竞赛数据集,网上有上千份分析(很多是抄的)。
  → 必须做差异化,不能写"我画了 DAU 曲线"这种基础分析。
  → 用本文档第三部分的 A→C→B→G→D 五切口组合,在网上现有作品里基本看不到。
- 9 天时间跨度短,做"传统月留存"不行,但能做 D1/D2/D3/D7 留存。

时间戳注意:数据里是 Unix epoch 秒级时间戳(+08 时区下解读),已在数据清洗
阶段确认窗口为 2017-11-25 00:00 ~ 2017-12-04 00:00。约 5.5 万行(0.056%)
timestamp 越界(范围 1902 ~ 2037),全部为 pv 行为,已在 DWD 层过滤。


备选:Yelp Open Dataset
=====================================

链接:https://www.yelp.com/dataset

定位:Yelp 是美国版的大众点评/美团点评,这是它的官方开放数据集。

规模:
  - business(商户表): 15 万家,带经纬度、营业时间、品类、属性
  - review (评论表)  : 690 万条,带文本 + 1-5 星 + 时间戳
  - user   (用户表)  : 200 万用户,有好友网络、累计评论数、Elite 标签
  - tip   (短评表)   : 90 万条
  - checkin(签到表)  : 商户按小时维度的到访模式
  - 时间跨度          : 14+ 年(2005 ~ 2022)
  - 总大小            : ~10 GB JSON

它相比 Taobao 的优势:
- 数据架构跟大众点评/美团点评/抖音本地生活完全对应
  (本地商户 × 用户 × 评论 × 社交关系 × 时空维度)
- 14 年跨度能做真实的长期留存曲线和 cohort 衰减

它的劣势:
- 中文语境感稍弱
- 数据架构相对复杂,学习曲线更高
- 国内分析师做得人少,但反过来也意味着面试官可能没听过

何时该用 Yelp 替换 Taobao:
- 如果发现 Taobao 上做出来的作品和网上现有的雷同度太高
- 如果用户做完 Taobao 后想再做一个差异化项目
- 如果未来想做"商户/POI 维度的本地生活分析",Yelp 是更好的载体

当前决定:Taobao UserBehavior 作为主选。Yelp 作为后续备选/补充。

[3] 项目执行方案:A → C → B → G → D 五切口
------------------------------------------------------------

3.1 五个切口(按执行顺序)
==========================

A. 假死用户识别 + 流失画像
--------------------------
做什么:在 9 天数据里,识别出"只在 Day 1-2 有行为后消失"的用户,对他们做
        画像,对比他们和高活用户在 Day 1 的行为差异。
输出:
  - "假死用户"定义指标(精确的 SQL/Pandas 规则)
  - 假死用户 vs 活跃用户的 Day 1 行为对比表
  - 干预建议(比如:Day 1 浏览了 X 类目但没加购的用户,Day 3 push 召回)
业务对应:本地生活/电商的"新人 7 日召回"策略
技术要点:窗口聚合、用户分群、对比统计


C. 探索型 vs 收割型用户分群
---------------------------
做什么:把用户分成"探索型"(浏览的类目分布广,但购买少)和"收割型"(浏览
        集中、目标明确就下手)。两类用户的商业价值完全不同,运营策略也不同。
输出:
  - 分群指标定义(类目宽度、PV/购买比、品类集中度等)
  - 两类用户的画像对比表(行为频次、活跃时段、品类偏好)
  - 业务建议:探索型适合内容推荐引流,收割型适合精准 push 复购
业务对应:用户分层运营、个性化推荐
技术要点:多维特征工程 + 业务规则分群(KMeans 仅作辅助验证)
**关键坑**:分群标签的好坏直接决定业务可解释性。纯 KMeans 出来的"3 群"如果
            讲不出业务区别就是失败。优先用业务规则定义阈值,聚类只作交叉验证。


B. 加购未付转化窗口分析
-----------------------
做什么:用户加购后多久放弃概率最大?加购后什么行为(浏览同品类、看替代品、
        看评价)预示会买?
输出:
  - 加购→购买的时间间隔分布
  - 加购后行为路径的转化漏斗
  - 转化条件分析(满足什么条件的加购最终转化率高?)
  - 业务建议:推 push 的最佳时机和文案方向
业务对应:电商 push 文案+时机,大厂常见运营优化场景
技术要点:事件序列分析、漏斗计算、生存分析(可选,加分项)


G. PV → Buy 转化率的时段差异分析
--------------------------------
做什么:不同时段(小时维度)下的 PV → Buy 转化率差多少?为什么白天比晚上转化
        高,或反之?哪些时段是"无效流量",哪些是"高质量流量"?
输出:
  - 24 小时维度的 PV、Buy 数与转化率曲线
  - 工作日 vs 周末的时段差异对比
  - 业务建议:推广预算的时段分配、push 推送的最佳时机
业务对应:营销投放优化、推送时机决策
技术要点:时段聚合 + 转化率定义 + 工作日/周末维度交叉
**关键坑 1**:转化率不能直接用 buy_count / pv_count(同一用户的 pv 和 buy 可能
              对应不同商品)。必须严格定义"转化"口径:用户级(看过任何 → 买过
              任何)还是 user-item 级(同一商品的 pv → 同一商品的 buy)。
**关键坑 2**:9 天里有 2 个周末(11-25/26 和 12-02/03),但后者是双 12 预热期,
              行为不代表正常周末。工作日/周末对比必须做敏感性说明。


D. 首日行为预测 7 日留存(建模 —— 压轴)
----------------------------------------
做什么:用每个用户 Day 1 的行为特征预测他在 Day 7-9 是否还活跃,然后给特征
        重要性排序,讲清楚"为什么 PV 数比加购数更重要"这类问题。
        前 4 个切口产出的用户分群、行为路径、时段特征都可以作为本切口的输入特征。
输出:
  - 留存预测模型(可用 logistic regression / lightgbm)
  - 特征重要性排序 + 业务解读
  - 模型评估(AUC / 准确率 / 业务意义而非纯技术指标)
业务对应:用户生命周期管理、新用户激活策略
技术要点:特征工程、防数据泄漏、模型评估、业务可解释性
**关键坑**:Day 1 特征 → Day 7-9 标签,严格不要用 Day 2-6 数据,
            否则就是泄漏。代码里强烈建议用 timestamp 边界做断言检查。


3.2 为什么是这 5 个 + 这个顺序?
================================
- 五个切口覆盖四种分析能力:画像(A)、分群(C)、路径漏斗(B/G)、建模(D)
- 五个切口共用同一份 DWD 层 Parquet,以及后续会产出的 DWS 层聚合表
  (用户日活跃、cohort 留存矩阵等),后续 ADS 层产出独立的画像/漏斗/模型文件
- 故事链:
  "新用户进来 → 谁会假死(A)→ 没死的人是哪种类型(C)→ 他们加购后的路径如何
   (B)→ 受时段影响怎样(G)→ 综合前面的洞察,谁会留下来(D)"
- 顺序的关键设计:D 作为压轴,可以把 A/C/B/G 产出的洞察(假死标签、用户分群、
  漏斗特征、时段特征)直接作为模型输入。先做 D 就用不上这些。
- 简历上是一个项目,但能讲五种深度,面试半小时绰绰有余

[6] 预期会踩的坑(提前打预防针)
------------------------------------------------------------

工程类:
1. pd.read_csv 直接 OOM
   → 用 DuckDB 读原始 CSV,直接转 Parquet。 后续都用 Parquet。
2. 时间戳解析错误
   → Taobao 数据是 Unix epoch 秒,不是毫秒。pd.to_datetime(unit='s')
3. 9 天窗口短,误把"Day 9 才出现的用户"当成新用户
   → 严格定义 cohort:用户的"首次出现日"是基准,只对 Day 1-2 出现的
     用户做后续留存分析。

分析类:
4. 假死用户的定义如果太松,会把"轻度活跃"也算进去
   → 多试几个定义,看分布形态是否合理。最终选一个能自圆其说的。
5. 加购未付分析里,如果用户 Day 9 加购,自然没付,但这不是"放弃"
   → 必须截尾处理,只看 Day 1-7 的加购,留 Day 8-9 看是否买。
6. 首日行为预测的数据泄漏
   → 特征严格只用 Day 1 当天数据。标签用 Day 7-9 的活跃状态。
     代码里强烈建议用 timestamp 边界做断言检查。

叙事类:
7. 做着做着只剩"图表展览"
   → 每个分析结束都问自己一句:"如果我把这张图给 PM 看,他能拿来做什么?"
8. 五个切口最后变成五个孤立报告,没有故事链
   → README 的第一章必须先写"故事链",然后五个切口是这个故事的五段。

v2 新增风险点(2026-05-17 Claude review 后补):

工程类:
9. 9 天窗口下"7 日留存"在严格意义上不成立
   → 只有 Day 1 出现的 cohort 才能完整观察到 D7。若用 Day 5 cohort 算 D7
     留存,观察期不够,数据是无效的。
   → 落地:cohort 留存矩阵必须明确标注"仅基于 Day 1-2 cohort"。后段 cohort
     只能算到 D{9-首次出现日} 为止。

分析类:
10. 切口 D 样本量风险
    → Day 1 → Day 7-9 标签建模,样本被砍到只剩 Day 1 出现的用户。98 万
      用户里 Day 1 占比可能只有 30-40%。
    → 落地:开始建模前先验证 Day 1 用户数 ≥ 几万。若不够,放宽到
      Day 1-2 cohort 或把标签改成"未来 3 天活跃"。

11. 假死用户阈值的敏感性
    → 不能只给一个"假死用户"定义就交差。至少做 3 个阈值版本(松/中/严)
      的对比,展示分布形态怎么随阈值变化,然后说清楚为什么最终选中间那个。
    → 这是面试被追问"为什么是这个阈值"时的标准答案。

v3 新增风险点(2026-05-18 加入切口 C / G 后补):

分析类:
12. 切口 C 分群的业务可解释性
    → 不要直接上 KMeans 就完事。先用业务规则定义"探索型"和"收割型",
      把判定阈值(类目宽度、PV/购买比等)做敏感性分析。聚类只作交叉验证。
    → 终极判断标准:能不能用一句话给 PM 讲清这两群人的差异。

13. 切口 G 转化率的口径陷阱
    → 不能粗暴用 buy_count / pv_count 算"转化率"。一个用户看了 A 商品却买了
      B 商品,把 A 的 pv 和 B 的 buy 都算进去,数字就被污染了。
    → 必须严格定义口径:用户级转化(用户在该时段看过任何 → 用户在该时段买过
      任何)或 user-item 级转化(同一 user_id+item_id 的 pv → buy)。
    → 第二个坑:9 天里 12-02/03 周末被双 12 预热污染,工作日/周末对比必做敏感性。

跨切口:
14. 切口 D 与前序切口的特征依赖
    → D 作为压轴,会用 A 产出的"假死标签"、C 产出的"用户分群"、B 产出的
      "加购特征"、G 产出的"时段特征"作为输入。做 A/C/B/G 时就要预留接口
      (产出标准格式的特征表),不要分析完就把中间结果扔掉。
